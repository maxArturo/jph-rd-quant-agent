# PRD: Data-Substrate Expansion — making news-driven research testable

**Story numbering:** continues the repo-wide sequence; this PRD is US-061..US-075.
**Prior context:** `tasks/prd-rdagent-q-trading.md` (source system), `tasks/prd-loop-hardening.md` (promotion gate), the c9587797 degenerate-refresh postmortem (docs/decisions.md 2026-08-18, main `0d47724`).

## 1. Introduction / Overview

The research loop's idea funnel and its data substrate no longer match. The operator's standing instruction is to center hypotheses on current news and sentiment, and the Slack advisor (Claude Tag) scans news daily — but the Qlib store contains only per-ticker daily OHLCV. Every news-driven idea therefore either dies at loop 0 (run #36: fuel-beta had to proxy Brent with the universe's own energy-heavy tail — circular, IC 0.0060, abandoned) or gets laundered into a generic price/volume proxy the loop would find anyway.

This PRD closes the gap in three phases:

- **Phase 0 (steering + pre-flight):** a machine-checked "data menu" so untestable ideas are parked *before* they cost a GPU run.
- **Phase 1 (market series):** energy + macro daily series (Brent, WTI, heating oil, natgas, gasoline, gold, dollar index, treasury yields) ingested from FMP as broadcast fields.
- **Phase 2 (news attention):** per-ticker daily news counts, then (gated) haiku-scored headline sentiment.

**The one hard rule throughout — refresh parity.** The c9587797 incident happened because a promoted strategy's inputs weren't reproducible at daily-refresh time: the paper book silently traded a degenerate prediction. A new data series therefore *exists* only when it is present in all four places: (1) the Qlib bin store, (2) the factor-source data folder the coder LLM reads, (3) the daily `rdq-data-refresh` path, and (4) the GPU worker's synced inputs (snapshot-hash aware). A series in fewer than four places is a bug, not a partial feature.

## 2. Goals

- A research suggestion that needs unavailable data is refused at directive-crafting time (seconds, CPU), never discovered at loop 0 (hours, GPU).
- The fuel-cost-sensitivity directive (#36), re-issued unchanged, runs on real energy series with no proxying.
- News-attention hypotheses ("does recency/volume of coverage predict the cross-section?") are expressible directly from store fields.
- Every new field passes an exact-weights refresh-parity check (re-predict Spearman ≥ 0.98 vs backtest pred) before any factor using it can be promoted.
- No lookahead: every new series is point-in-time by publication/observation timestamp.

## 4. Functional Requirements

- FR-1: `data/menu.py` must derive the field inventory from the store itself; the checked-in doc must fail a test when stale.
- FR-2: The directive pre-flight must verify `data_required` entries programmatically against the menu; a missing series must block launch and produce a "parked — needs ingestion" thread reply naming the series.
- FR-3: Every new series must exist in all four places (bin store, factor-source folder, daily refresh, worker-synced inputs + snapshot manifest) before any factor referencing it may be nominated to the gate.
- FR-4: Market-level fields must be broadcast per instrument as `$mkt_<name>`, raw (never price-adjusted), forward-filled across source holidays.
- FR-5: News-derived fields must apply the 16:00 ET publication cutoff; nothing published after a day's close may appear in that day's value.
- FR-6: `$news_ct_1d` uses 0 for no-news days; `$news_sent` uses NaN for no-news days; both conventions documented in the factor-folder README.
- FR-7: Sentiment scores are write-once per (ticker, date); scoring prompt and model version are recorded with the series.
- FR-8: The refresh-parity harness must pass (Spearman ≥ 0.98 exact-weights re-predict) for every new field before the phase that introduced it is called done.
- FR-9: All FMP access goes through the existing OneCLI identities (`rdq-research` for builds/probes, `rdq-exec-paper` for the pre-open refresh); no new credentials, no keys in code or env.
- FR-10: Daily ingestion failures (FMP outage) must degrade to forward-fill + Slack warning; they must never block the 08:00 ET rebalance chain.

## 5. Non-Goals (Out of Scope)

- **Phase 3 — earnings/fundamentals events** (earnings calendar, surprises, accepted-date PIT discipline): explicitly deferred to a future PRD, gated on Phases 1–2 demonstrating the loop can exploit exogenous data.
- Intraday data of any kind; everything here is EOD.
- Social-media scraping or non-FMP news vendors; sentiment is derived from FMP headlines only.
- Changes to the promotion gate, its thresholds, or the loop's model-pin enforcement (separate workstream from the audit).
- Backtesting infrastructure changes; new fields ride the existing store/refresh/factor-source machinery.
- Live trading anything.

## 6. Technical Considerations

- **Refresh recovery math:** `data/refresh.py` recovers raw equity values as `stored/factor`; market and news fields are stored raw with an implicit factor of 1, so the identity holds — but the rebuild path must be taught which fields skip adjustment (US-066/067).
- **RD-Agent linking contract:** every file in `data_folder/` is linked into each factor workspace and described to the LLM via the README; `data_folder/` and `data_folder_debug/` must carry the same filenames (`make_factor_source.py` docstring). New companion files follow this or the coder never sees them.
- **Snapshot staleness:** GPU snapshots are selected by `worker_inputs_hash`; adding the series manifest to the hash (US-068) is what prevents a pre-expansion snapshot from serving a post-expansion run. This is the same mechanism that pinned `research/install.sh` after the litellm incident.
- **Incumbent unaffected by construction:** e05ad9b4's factors reference only OHLCV fields, so its gate-time recompute and daily refresh are unchanged; US-069 should still run once against the incumbent as a regression check.
- **Backfill is the slow part of Phase 2:** run it once, checkpointed, throttled per US-071's measurements; the daily incremental is small.

- Directive #36 re-run produces a real fuel-beta factor at loop 0 (no proxy) and reaches a gate verdict.

## 8. Open Questions

All four original questions are resolved (2026-08-24):

1. **Dollar index / treasury availability — RESOLVED, available.** `DXUSD` serves the dollar index via the standard EOD endpoint (full window coverage); `/stable/treasury-rates` serves the full curve back to 2025-01-02 but truncates any request wider than ~90 calendar days, so the client chunks (US-064/065). No substitutes needed.
2. **News history depth — RESOLVED, sufficient.** Per-ticker history reaches at least 2025-01-02 (the store start) on the current plan, pagination works (250/page), and `publishedDate` is second-resolution US/Eastern. Thin names are legitimately sparse (ASAN: 1 article in Jan 2025) — handled by the 0-for-no-news convention, not a data gap. Only the rate-limit/throttle measurement remains, inside US-071.
3. **Count transformations — DECIDED: raw only.** `$news_ct_1d` ships as the raw count. Log-scaling, z-scoring, and windowing are the factor coder's job; pre-baked variants bloat the menu and multiply the four-place integration burden. The README states this explicitly so the coder knows transformations are expected of it.
4. **Sentiment aggregation — DECIDED: per-article daily mean only.** One field, `$news_sent`. The deciding argument: US-072 archives raw article records (ts, headline, score once US-074 lands), so any alternative aggregation (count-weighted, intra-day recency-weighted) can be backfilled from the archive later as a new field with full PIT integrity — the choice is reversible, so start minimal. Intra-day structure is otherwise lost at daily aggregation, which is why the archive, not the aggregate, is the durable artifact.
